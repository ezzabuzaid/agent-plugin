# Rulings behind housekeeping

Each entry gives the rule, the user's words with their date, what happened, and the source.

## The two stops

**A turn never ends to wait on the user.** _"Keep in mind, I don't read your response, so you must use the tool to ask me any questions or to take any decisions from me."_ (2026-11-17). AskUserQuestion returns the answer inside the turn, so "waiting on the user" is not a reason to stop. A turn stops only when it is Finished or Parked. `experiments-mutex/ask-all-needed-inputs-at-once.md`

**Ask everything at once, from the session's first message.** _"use ask user question for any input you need from me from the begining of this session to finish everything. if nothing more to do run housekeeping."_ (2026-11-16, typed four times that day). Earlier forms: _"Like anything that we have forgot this whole session and the stuff that we need"_ (2026-11-12), _"when you need things from me use ask user question to have my input. don't wait"_ (2026-11-13).

## Ask

**The week of nudges.** Between 2026-11-07 and 2026-11-17 the user typed a form of "what are you waiting for? / do you need anything from me? / use ask user question for any input you need" about 17 times in 14 sessions. The replies just before 8 of those nudges:

- 2 gave the user a task in prose: _"Still waiting on you at the mini: the four System Settings toggles … One run in Terminal"_; _"Cleanup that's yours, through Mole"_.
- 4 waited on background work or a peer, with the user's decisions not asked: _"The study lockfile retry and commit B's test gate are both running in the background. I'll pick up each one when it finishes."_; _"Commit B hasn't landed. … It will message me when B is on HEAD."_; _"The tool commit is waiting on Docker Desktop."_
- 2 ended on open items: _"Still to do after commit B lands: Phase 3 …, then Phase 4"_; a table whose rows said _"needs a design choice"_.

These are the four Ask gotchas: idle, a task is a question, open items are questions, remaining phases hide decisions.

**Tried and dropped: "a next step with an open design choice is a question now".** In the Mac mini session the reply ended _"After that I'll install the always-on phone server"_. After the nudge, the user's first decision was _"How should the CLI Remote Control cover all repos on the mini?"_ Neither the old skill nor this one asked it in the 2026-11-17 replay. The user chose "iterate now". A gotcha for it was added and replayed on the same three cases: it made the agent ask more design choices (cut-over, memory home, backlog on the mini), but still not the Remote Control one, and the total stayed at 7 of 9 checks (old skill: 5 and 4 of 9). By the rule set before the run, it was removed. Workspace: `~/.claude/scratch/housekeeping-workspace/iteration-2/`.

**Pushes are not hidden decisions.** _"you can push whatever you want. no need to ask for it"_ (2026-11-17); _"They should be able to commit and push on certain repositories without asking me and without needing to justify anything."_ (2026-11-18). From 2026-11-13 to 2026-11-18, about 40 AskUserQuestion calls asked whether, when or who should commit or push in the user's own repos. The user answered yes or "push everything" to nearly all of them, and 15 came after the 2026-11-17 words. The "remaining phases" gotcha named "pushes to other repos" and "overrides of a peer's hold" as decisions to find, so each sweep asked one; both were removed. Which pushes need the user is policy in the user's harness (settings and hooks), not skill text: _"policy as a code instead of instruction"_ (2026-11-18).

**Every ask goes through AskUserQuestion** (the "explanation inside it" half is overruled; see "The chat explains, the dialog only asks" below, 2026-11-24). _"From now on, you must use ask user question to ask me, not fucking replay and stuff."_ (2026-11-20). Earlier that day the skill had a carve-out: a choice that needed an explanation was written in chat with "My pick:", ended on "Reply A, B or C", and `ask-in-the-tool` stayed quiet on it. It came from three rulings: _"answer me in chat not in the dialog box"_ and _"don't answer in the dialog for god sake. I cannot see your answer"_ (2026-11-19), and _"you need to explain those tickets to me as if I am 5"_ (2026-11-20). The carve-out lasted about an hour. Five turns ended on a prose "Reply …" while background notifications kept arriving, and the user then gave the ruling above. What the earlier rulings protect still holds: an open dialog hides the chat, so the explanation goes inside the dialog (the question, the option descriptions, a preview for code). Text written before the dialog, or a dialog that only says "see above", is not read. `ask-in-the-tool` now also fires on a sentence that starts "Reply" and gives an answer format. `January-text2sql/feedback_explain_inside_askuserquestion.md`

**Ask only what is the user's.** The agent decides what the design decides, and asks only on a real split. A question already answered costs the user a second read. `experiments-mutex/decide-correct-design-not-preference.md`, `experiments-mutex/dont-reask-pending-decision.md`

## Running work

**Count running work from the harness, not from memory.** On 2026-11-20 a handoff said _"Nothing of mine is running or uncommitted"_ while a subagent it had started (deepagents #3369, 78 tool calls) was still editing 20 files of the shared checkout. The subagent lived through the `/clear`, and its report reached the new context, which had never started it. One turn after the Stop reminder said _"Background work is still running"_, the new context repeated the claim (_"Still running: nothing. I started no background work."_). Both statements came from memory, and `ListAgents` listed the subagent the whole time. The idle reminder now names each task by kind, id and description.

**Running work is no reason to stop working.** _"Can't you start on something while it's releasing?"_ (2026-11-20), _"Can't you do some work whilst you're waiting?"_ (2026-11-20, a second session), _"cannot you do work whilst shell is running?"_ (2026-11-21). Each time the agent asked its questions, did the record jobs and ended the turn on a CI, release or npm watch, while decided work waited on nothing that ran: sdk-it #3923 (1), #4901 and #4907; #5006; #5127's exploration and plan. The Idle row ended "then wait" and the `housekeeping-due` reminder "then keep waiting", and the agent followed them over its own memory. The 2026-11-20 reflection named the fix; it landed on 2026-11-21. `January-sdk-it/feedback_work_while_waiting.md`

## Why a Stop gate sends the agent here

**This skill did not run itself.** Its earlier description said "use it without being asked while waiting on subagents, CI, a deploy or a long shell command". The idle stalls above happened anyway.

**The hooks before the gate (week to 2026-11-17, 2876 stops).** A Haiku prompt Stop hook blocked 114 times, 107 of them on running work that its own rule allowed, 28 in a row in one session. It let "waits for the user" end a turn, which is the stall the user nudged about. The every-third-prompt backlog audit added 303 turns, and 4 of them led to an agent-backlog call. The regex hook for prose questions blocked 102 times and had no phrase for a task or a wait on the user.

**One gate, judgement in the main agent.** _"I think we need to rethink out stop hooks altogether to achvie those. we need to decombse and think form first princple"_ (2026-11-17). The user chose "One gate + housekeeping" and "After new work". Code checks what a machine can see (a prose ask in the final message, new tool calls since the last sweep, running background tasks). The main agent, which has the whole context, does the judgement here. The rules are `ask-in-the-tool` and `housekeeping-due` in agent-plugin `hooks/ezzs-way-of-coding`.

**A folder, not one crammed file.** _"make sure we use proper skill file/folder structure so we don't cram the main skill file"_ (2026-11-17). **Records gotchas.** "Edit the doc, do not file it" and "name what you checked" come from the first version (2026-11-10). The source of those two was not recorded.

The corpus: every housekeeping Skill call after fc1cdd2 (2026-11-21 14:08Z), 98 calls in 77 sessions in 11 projects. Nine agents mined 53 sessions with a correction and 6 control sessions from one brief; every one of their 394 quotes was checked against the session file it names (388 at the cited line). The merge has 27 groups, ranked by independent sessions. Session ids below are the first 8 characters of the transcript name; "line N" is its JSONL line. Workspace: `~/.claude/scratch/housekeeping-workspace/forensics-2026-11-26/` (`merge.md`, `guardrails.md`, `reports/`).

**The skill was rarely in front of the agent.** In 2,520 stops, `housekeeping-due` fired 2,297 times; 74 were followed by a Skill call. Most sweeps ran from memory, and most findings below came from such sweeps (aca548da line 6508: _"you finished everything? are you sure? double check"_ after a sweep with no Skill call). So the Stop rule now fires on a real change or before a close claim, and only a Skill call satisfies it; the description says so.

**An answer ends the turn** (23 sessions, the largest group). The Stop rules sent a sweep, and the sweep a dialog, right after the agent answered the user's question: _"answer my question first"_ (aca548da line 771), _"answer my question man"_ (881553d1 line 3640; the agent: _"The dialog I opened right after my answer hid it."_). Rulings of 2026-11-16 and 2026-11-18 already said it; no skill line or hook did.

**Idle never waits on a test run, a gate, CI, a push or a deploy** (19 sessions).
